# C5.3.1 / C5.3.2 — Protocole d'intégration et automatisation

**C5.3.1** — déployer systèmes et équipements avec une méthode d'intégration adaptée (IaC).  
**C5.3.2** — automatiser déploiements et actions récurrentes (playbooks, systemd, remédiation).

---

## 1. Choix de méthode (C5.3.1)

| Option écartée | Pourquoi |
| --- | --- |
| Ansible depuis l'hôte Windows | WinRM / chemins / Vault sur `vboxsf` (fichiers vus exécutables) |
| Install manuelle des 3 Debian | Non rejouable, hors critère « protocole argumenté » |
| Un seul playbook lancé en SSH croisé | Contredit le cloisonnement (Admin ne doit pas « posséder » Prod) |

**Méthode retenue** : Vagrant crée les VMs et le réseau ; **chaque invité** exécute `ansible-playbook` en local (`ansible_local`) avec `--limit` sur son groupe (`prod` / `router` / `admin`).

Justification :

- L'hôte reste un poste SRE Windows, pas un nœud d'orchestration.
- Le mot de passe Vault est écrit sur le disque ext4 de la VM (`/etc/ansible-vault-pass.txt`), pas dans le partage VirtualBox.
- L'ordre `site.yml` (common → fw-router → web-prod → supervision) suit les jalons : on ne supervise pas avant d'avoir cloisonné.

Fichiers : `Vagrantfile`, `ansible/site.yml`, `ansible/inventory/hosts.ini`.

---

## 2. Protocole d'intégration (étapes)

1. Prérequis hôte : VirtualBox, Vagrant, RAM ~4 Go, clone Git.
2. `cd` dans le projet → `vagrant up` (premier run : box + téléchargements).
3. Sur chaque VM, dans l'ordre du `Vagrantfile` : shell Vault → `ansible_local` `site.yml --limit <groupe>`.
4. Contrôle interfaces : `ip -br a` (attendu `eth1`/`eth2`, cf. DAE).
5. Recette A puis B, C, D (`docs/tests-de-validation.md`).
6. Remise en service : Grafana `https://127.0.0.1:3443`.

Rejeu après incident : `vagrant provision` (idempotent) ou `vagrant destroy <vm> && vagrant up <vm>` si l'hôte est brûlé, puis recette ciblée.

## 3. Automatisation (C5.3.2)

| Couche | Mécanisme | Action récurrente évitée |
| --- | --- | --- |
| Infra | Vagrant | Création manuelle des 3 VMs / IPs / `intnet` |
| Config | Rôles Ansible (`common`, `fw-router`, `web-prod`, `supervision`) | nftables, TLS, Zabbix, Grafana à la main |
| Persistance | Unités systemd (routes, exporters, Loki, healer…) | Re-saisie après reboot |
| Remédiation | Alertmanager → webhook → `healer` (sudoers 1 commande) | Astreinte pour un Nginx down |

Gains : reconstruction rejouable, même état sur les 3 zones, remédiation < 60 s sans compte root partagé.

Hors automate (volontaire) : correctif OpenSSL PSK si le bug Debian 12 réapparaît ; pas de job de **backup** (PRA = rebuild, DAE § 3.2).
