## 1. C5.1.1 — Cartographie de l'existant

### 1.1 Contexte métier

M2-Shop est une plateforme de commerce électronique. Le fil rouge du PoC est un serveur web public (Nginx) : vitrine HTTPS, logs d'accès, disponibilité du catalogue. Les parties prenantes sont :

- **Métier / clients** : le site doit rester joignable (HTTP → HTTPS).
- **SRE / exploitation** : voir la santé de la prod (métriques, logs, alertes) sans se connecter en SSH permanent sur le serveur web.
- **RSSI / conformité** : aucun collecteur en clair, aucun tunnel Admin → Prod hors matrice, preuve d'audit des flux refusés.

### 1.2 SI « avant » (constat d'existant type)

Avant le PoC, l'architecture type d'une boutique de cette taille présentait les écarts suivants — c'est le **point de départ** que le projet corrige :

| Composant | État constaté | Risque |
| --- | --- | --- |
| Serveur web | Unique, même LAN que l'admin ou NAT plat | Mouvement latéral, pas de zone de confiance |
| Supervision | Absente, ou scrape SNMP/HTTP sans auth | Pas de détection de panne Nginx, pas de preuve |
| Collecte | Agent Zabbix passif (le serveur initie vers la prod) | Flux Admin → Prod non maîtrisé |
| Journalisation | Logs locaux sur le web, non centralisés | Ineexploitable dès que la VM est coupée |
| Remédiation | Redémarrage manuel, root partagé | RTO > 60 s, surface d'administration trop large |
| Filtrage | iptables permissif ou aucun FORWARD documenté | Impossible de démontrer le Zero-Trust |

Il n'existait pas de **matrice de flux réglementaire** ni de reconstruction IaC : un incident impliquait une reconstruction à la main, non rejouable.

### 1.3 SI cible du PoC (cartographie à date)

Trois machines Debian 12, aucun réseau privé commun entre production et administration. Tout flux inter-zones transite par `fw-router`.

```
                    Hôte SRE (Windows)
                     | NAT / vagrant ssh
                     | Grafana 127.0.0.1:3443
                     v
web-prod (10.0.20.20) <--> fw-router (.20.1 / .10.1) <--> supervision (10.0.10.5)
   DMZ Production              cloisonnement                    DMZ Admin
   Nginx, Node Exporter,       nftables DROP                    Prometheus, Loki,
   Zabbix Agent2, Promtail,    routes inter-zones               Grafana, Zabbix,
   webhook healer                                               Alertmanager
```

| Zone | Hôte | Rôle dans le SI |
| --- | --- | --- |
| DMZ Production | web-prod 10.0.20.20 | Service client (Nginx) + collecteurs sortants / exposés selon matrice |
| Inter-zones | fw-router 10.0.20.1 / 10.0.10.1 | Seul routeur, politique DROP, 4 flux FORWARD |
| DMZ Admin | supervision 10.0.10.5 | Supervision centralisée, alerting, dashboards |
| Hôte | poste SRE | Pilotage Vagrant, accès Grafana (port-forward), pas Ansible distant |

**Cartographie applicative :**

- **Métier** : Nginx (80/443, INPUT web-prod uniquement).
- **Métriques** : Node Exporter (9100, TLS 1.3 + Basic Auth) ← Prometheus (PULL).
- **Disponibilité agent** : Zabbix Agent2 → Zabbix Server (10051, PUSH, PSK).
- **Logs** : Promtail → Loki (3100, HTTP isolé).
- **Pilotage** : Grafana HTTPS (3000 / `127.0.0.1:3443`).
- **Remédiation** : Alertmanager → webhook 9095 (HTTP, écart assumé) → compte `healer`.

Le détail des flux (FORWARD vs hôte) est dans `docs/matrice-de-flux.md` et le DAE § 1.4.

### 1.4 Écart existant → cible (synthèse)

| Besoin | Avant | Après (PoC) |
| --- | --- | --- |
| Cloisonnement | LAN plat | 2 `intnet` + routeur dédié |
| Qui initie la supervision | Souvent l'admin vers la prod | Zabbix en push ; Prometheus seul flux Admin→Prod métier (9100) + webhook 9095 |
| Preuve de refus | Absente | Timeout port 22, logs nftables |
| Reconstruction | Manuelle | `vagrant up` + `ansible_local` |
| Panne Nginx | Astreinte humaine | Alerte + relance < 60 s (validé 7 sept. 2026, 21:13:44 UTC) |

## 2. C5.1.2 — Orientations stratégiques et contraintes

### 2.1 Orientation stratégique

L'orientation du projet n'est pas « installer Grafana ». Elle est de **rendre l'observabilité compatible avec un modèle de zones de confiance** :

1. La production reste exposée au public (boutique).
2. L'administration ne s'ouvre pas pour autant.
3. Chaque flux inter-zones est justifié, chiffré quand le sujet l'exige, et testé.
4. Une panne du service web est détectée et contenue sans root partagé.

Cela aligne le SI sur une logique ANSSI (moindre privilège, défense en profondeur, traçabilité) tout en servant l'objectif métier (disponibilité M2-Shop).

### 2.2 Contraintes réglementaires et de sécurité

| Contrainte | Traduction dans le PoC |
| --- | --- |
| Guide d'hygiène / Zone Trust | DROP par défaut ; collecteurs bornés à `10.0.20.20` sur supervision |
| Pas de flux fantôme | SSH, DNS, ICMP, site public déclarés en plan **hôte**, pas en FORWARD |
| Preuve de chiffrement | TLS 1.3 Node Exporter, PSK Zabbix, captures / 401 |
| Moindre privilège d'exploitation | `healer` : une commande sudo exacte, pas de shell |
| Traçabilité d'incident | PCO : isolation FORWARD + artefacts vers `/vagrant` (pas de SCP inter-zones) |

**Écart assumé (à ne pas cacher au jury)** : webhook 9095 et Promtail→Loki en HTTP. Acceptable en `intnet` de labo ; interdit tel quel en production (mTLS).

### 2.3 Contraintes métier

- Le site public doit survivre au cloisonnement : 80/443 restent en INPUT web-prod, **hors** fw-router.
- RTO de remédiation Nginx : **< 60 secondes** (sujet). Mesuré à ~0,2 s une fois l'alerte reçue (21:13:44).
- RTO de reconstruction d'une VM : IaC (`vagrant destroy` / `vagrant up`), pas une install manuelle.
- **Pas de backup applicatif** dans le périmètre : le PRA est la reconstruction, pas un restore (dumps Zabbix/Grafana/Loki hors sujet pédagogique). Détail : DAE § 3.2.
- Le SRE doit piloter depuis Windows sans installer Ansible sur l'hôte.

### 2.4 Contraintes techniques

| Contrainte | Impact architecture |
| --- | --- |
| Hôte Windows + VirtualBox | Provisioning **uniquement** `ansible_local` dans chaque VM (`--limit`) |
| Partage `vboxsf` | Mot de passe Vault posé dans `/etc/ansible-vault-pass.txt`, hors `/vagrant` |
| Deux `/24` disjoints | Routes statiques systemd obligatoires (sinon NAT, Zero-Trust inopérant) |
| Box `debian/bookworm64` | Noms d'interfaces à vérifier (`eth1`/`eth2` vs `enp0s*`) |
| RAM limitée (~3,5 Go VMs) | Mono-instance, pas de HA — assumé pour le PoC |
| Certificats auto-signés | `insecure_skip_verify` Prometheus ; Grafana « Non sécurisé » dans le navigateur |

### 2.5 Contraintes environnementales (périmètre du PoC)

Le PoC n'est **pas** un SI de production : pas de PKI d'entreprise, pas de bastion nominatif, pas de SSO Grafana, secret Vault de labo. Ces limites sont des **contraintes de cadre pédagogique**, pas des oublis. Elles sont listées pour que le jury distingue :

- ce qui est **démontré** (zones, IaC, recette, auto-healing) ;
- ce qui serait **industrialisé** ensuite (secrets, mTLS, HA, bastion, **sauvegardes**).

### 2.6 Parties prenantes et objectifs (entrée C5.2.1)

| Partie prenante | Objectif | Couvert par |
| --- | --- | --- |
| Direction / métier | Boutique disponible | Nginx + auto-healing |
| SRE | Voir et agir sans SSH prod permanent | Grafana, Prometheus, Loki, webhook |
| RSSI | Flux justifiés, chiffrement, preuves | Matrice, nftables, DAE § 2.3 |
| Formateur / jury Bloc 5 | Recette rejouable, IaC argumenté | `tests-de-validation.md` + `vagrant up` |
